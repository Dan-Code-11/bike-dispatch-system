01 · Overview

Project Overview

BikeDispatch is a full-stack bike-sharing rebalancing decision support system designed for Manhattan's Citi Bike network. It addresses the classic "tidal mobility" problem — commuter-driven demand surges that leave some stations empty and others overstocked — by combining predictive analytics, optimization algorithms, and interactive geospatial visualization in a single operational dashboard.

The system ingests 151 days of real Citi Bike trip history (Jan–May 2025), reconstructs station-level availability at 5-minute resolution, trains an LSTM model for multi-horizon demand forecasting, and computes optimal vehicle redistribution plans using a min-cost flow solver. All results are presented through a dark-mode, Uber-inspired UI with live WebSocket updates.

Frontend

Built with Vue 3 Composition API and Vite, the frontend features 9 routed views, a shared AppShell layout with sidebar navigation, and reusable components (MapView, PredictionChart, SpatialLab). State is managed via reactive refs with WebSocket-driven live updates on the dispatch dashboard.

Backend

The FastAPI backend exposes REST endpoints for prediction, dispatch, analytics, and alerts, plus a WebSocket endpoint (/api/ws/live) pushing station snapshots every 2 seconds. The data generator service loads pre-computed NPZ cubes and simulates real-time playback by indexing into historical time slices.

03 · Data

Data Pipeline

The data pipeline transforms raw Citi Bike trip records into structured, analysis-ready data cubes. All processing is deterministic and reproducible via the prepare_trips.py script.

Step 1 · Raw Trip Ingestion

5 monthly Parquet files (2501–2505) containing ~4.3M Citi Bike trips with start/end station IDs, timestamps, lat/lng, and rideable type. Filtered to a 2km buffer around Washington Square Park, retaining the top 30 stations by trip frequency.

Step 2 · Zone Generation

Each station is buffered into a GeoJSON polygon zone (manhattan_zones.geojson) with properties including zone_id, name, and trip frequency. These zones serve as the spatial units for all analytics and visualization.

Step 3 · Temporal Aggregation

Trip events are aggregated into 5-minute bins (288 slices/day) to produce station-level inflow/outflow counts. A cumulative inventory model tracks bike availability across the network, conserving total fleet size (~1,134 bikes) with ±1.2% daily fluctuation from in-transit vehicles.

Step 4 · Data Cube Serialization

Results are stored as NumPy NPZ files: bikes_5min.npz (151×288×30 availability matrix) and trips_5min.npz (flow matrix). This columnar format enables O(1) time-slice lookup for real-time playback and sub-second analytics queries.

Step 5 · Feature Engineering

For LSTM training, sliding windows of 24 historical steps (2 hours) are constructed with station embeddings, time-of-day encoding, and day-of-week flags. The train_ready.npz file stores pre-windowed features to avoid repeated computation during training.

05 · Prediction

LSTM Multi-Horizon Demand Forecasting

The prediction engine uses a MultiHorizonLSTM architecture with station embeddings and a dual-head output design to simultaneously predict discrete horizon anchors (1h, 2h, 3h) and a full 3-hour demand curve.

Model Architecture

# MultiHorizonLSTM — dual-head design Input: [batch, seq_len=24, features] # 2h history @ 5min ├── Station Embedding: 30 → 16 dims ├── Time Encoding: sin/cos hour + day_of_week └── LSTM Stack: 2 layers × 128 hidden, dropout=0.2 ├── Head A (Anchors): 3 discrete points (1h/2h/3h need) └── Head B (Curve): 36 steps × 5min = 3h full trajectory Loss: MSE(anchors) + λ × MSE(curve), λ=0.5 Optimizer: AdamW, lr=1e-3, cosine schedule Weights: lstm_weights_multi.pth (~940KB)

Baseline Comparison

The model is evaluated against a persistence baseline (last observed value carried forward). Improvement is measured as percentage reduction in MAE across all horizons and stations.

The POST /api/predict endpoint accepts a time anchor, 24-step history array, and zone order, returning per-station forecast anchors, full curve, and baseline evidence for comparison. Results include forecast_anchors, series_by_zone, and baseline_evidence with per-horizon MAE metrics.

06 · Optimization

Dispatch Optimization — Min-Cost Flow

The dispatch module solves a minimum-cost maximum-flow problem on a bipartite graph of surplus stations (sources) and shortage stations (sinks). The objective is to minimize total rebalancing distance while satisfying all demand constraints.

Problem Formulation

# Min-Cost Flow Formulation Given: - Surplus set S: stations with predicted need < -threshold - Shortage set D: stations with predicted need > threshold - Supply s_i = |need_i| for i ∈ S - Demand d_j = need_j for j ∈ D - Cost c_ij = distance_between(i, j) × 100 # integer weights Minimize: Σ Σ c_ij × x_ij Subject to: - Σ_j x_ij ≤ s_i (supply constraint) - Σ_i x_ij = d_j (demand satisfaction) - x_ij ≥ 0, integer (integral flow)

Algorithm: Successive Shortest Path (SSP)

The solver uses an integer-weighted Successive Shortest Path algorithm with Bellman-Ford for negative-cost residual edges. Weights are scaled by ×100 and rounded to integers, eliminating floating-point precision issues. This replaces the earlier networkx min_cost_flow (network_simplex) which took 20+ seconds on 87-vehicle scenarios.

Routing Geometry

Each dispatch plan includes real street-network geometry via OSRM (/route/v1/driving). Routes are cached per station-pair (round-trip shared), with endpoint anchoring correction to ensure routes connect exactly to station coordinates. OSRM-unavailable scenarios gracefully degrade to straight-line geometry.

07 · Spatial Analytics

Spatial-Temporal Analytics

The Spatial Analytics Lab provides four complementary lenses on the bike-sharing network, each answering a distinct analytical question about spatial patterns and temporal dynamics.

⏱️

Time-Series Playback

24-hour space-time cube animation showing station-level availability, need, or capacity-ratio across 288 time slices. Playback controls with adjustable speed (0.5x–8x), scrubber slider, and frame-by-frame navigation. Full-screen mode with 30-station sorted tooltip.

🔀

OD Tidal Flow Arcs

Origin-destination flow visualization using quadratic Bézier curves with 18% midpoint offset to prevent A→B/B→A overlap. Three-channel visual encoding: color (hue 40→0 = high→low flow), line weight (1.2–8px), and opacity (0.55–0.9). Top-K filtering (20/40/60) with flow labels on major routes.

📈

Moran's I + LISA

Global spatial autocorrelation (Moran's I with Cliff & Ord variance, normal-approximation p-value) plus Local Indicators of Spatial Association (Anselin 1995, 199 conditional permutations). KNN (k=3/5/7) or distance-band (500/800/1200m) weight matrices. HH/LL/HL/LH/NS cluster classification with Moran scatter plot.

📅

Typical Day Comparison

Weekday vs weekend average curves computed from all 151 days (~108 weekdays, ~43 weekends). Three view modes: aggregate average, top-5 high-variance stations, and ±1σ confidence bands. Key metrics: peak time shift (minutes), tidal ratio (weekday peak / weekend peak), and peak magnitude comparison.

The shared MapView component uses Leaflet with Esri World Imagery tiles (with OpenStreetMap fallback and 3-second timeout caching). Stations are rendered as unified black-dot circle markers with color-coded status rings. Dispatch routes use OSRM GeoJSON polylines with the accent color. OD flows use custom SVG Bézier arc overlays with three-channel encoding (color + weight + opacity).

Chart System

All charts use ECharts 5 with consistent dark-theme configuration. Key design decisions include: data-layer/marker-layer separation for time-series playback (chart drawn once, current-time indicator as pure DOM overlay), sorted tooltips with station name mapping (zone_id → name), full-screen mode with ESC exit, and adaptive y-axis ranges with nice rounding to 5-unit increments.
